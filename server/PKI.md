# Development PKI and production CA boundary (TASK-117)

This document describes the certificate authority (CA) practice for the
Kitchen LED Controller ThingsBoard deployment:

- **Development** — a short-lived private CA generated on this host by the
  scripts in `server/scripts/`. It signs the LAN server certificate for
  `home-assistance.local`, and devices integrate against it by installing
  only the public root at `/cert/ca.crt`.
- **Production** — the *procedures* for a protected, preferably offline, CA
  whose private key never lives on the ThingsBoard runtime host. No
  production material is generated by anything in this repository; the
  scripts and this document only describe the boundary and the ceremony.

Public ACME cannot normally validate private LAN names, so both environments
rely on a private CA rather than a public certificate. The server certificate
must always carry SAN `DNS:home-assistance.local`, exactly — the scripts enforce this and the
validation checks confirm it.

---

## 1. Endpoint identity

| Item                          | Value                       |
|-------------------------------|-----------------------------|
| Documented LAN endpoint       | `home-assistance.local`     |
| Server certificate DNS SAN    | `DNS:home-assistance.local` (only entry) |
| MQTT TLS endpoint             | `mqtts://home-assistance.local:8883` |
| HTTPS admin endpoint          | `https://home-assistance.local:443` |
| Default CA subject            | `/O=Kitchen LED Controller Dev/CN=hq-dev-tb-ca` |

The documented name can be overridden per-deployment with `TB_DNS_NAME` in
`server/.env` or `--dns-name` on the phase scripts, but the whole pipeline
(CSR creation, signing, validation) enforces whatever name is resolved so a
certificate can never silently be issued for another host.

## 2. Development CA — scripts

The development PKI is split into three focused scripts sharing one
configuration (`server/scripts/dev_pki_config.sh`); `gen_dev_tls.sh`
orchestrates them for the compose stack.

| Script                              | Generates                          | Idempotent / destructive          |
|-------------------------------------|------------------------------------|-----------------------------------|
| `server/scripts/gen_dev_ca.sh`      | root CA `ca.key` + `ca.crt`        | keeps existing; `--regenerate` |
| `server/scripts/gen_server_csr.sh`  | server `server.key` + `server.csr` | keeps existing; `--force`      |
| `server/scripts/gen_server_cert.sh` | `server.crt` (+ `server.pem`, `server_key.pem`, `server.ext`) | keeps existing; `--force` |

Workflow:

```bash
server/scripts/gen_dev_ca.sh                                    # 1. root CA
server/scripts/gen_server_csr.sh --dns-name home-assistance.local  # 2. key + CSR
server/scripts/gen_server_cert.sh --dns-name home-assistance.local  # 3. sign CSR
python3 server/scripts/check_pki.py                             # 4. validate
```

`gen_dev_tls.sh` is the one-shot equivalent that also creates `server/.env`
secrets and the PostgreSQL data directory:

```bash
server/scripts/gen_dev_tls.sh               # idempotent setup
server/scripts/gen_dev_tls.sh --regenerate  # fresh CA + server key/CSR + cert
```

All output goes to the git-ignored `server/certs/` (and the tests use a
scratch directory via `--cert-dir`), so no key or certificate is ever
committed.

### 2.1 SAN requirement (enforced)

- `gen_server_csr.sh` writes `subjectAltName=DNS:<endpoint>` into the CSR.
- `gen_server_cert.sh` parses the CSR's SAN and **refuses to sign** unless it
  is exactly `DNS:home-assistance.local` (or the resolved override):
  ```
  gen_server_cert.sh: REFUSING to sign - CSR SAN is 'DNS:wrong.example.com'
    required SAN: DNS:home-assistance.local (the documented endpoint)
  ```
- `check_pki.py` asserts the issued certificate's SAN set equals
  `{DNS:home-assistance.local}`.
- `check_endpoints.py` verifies the live endpoints with hostname verification
  enabled (`check_hostname=True`).

## 3. Certificate profiles

### 3.1 Development root CA (`ca.crt`)

| Field              | Value                                    | Why |
|--------------------|------------------------------------------|-----|
| Key algorithm      | RSA 4096                                 | long-lived trust anchor |
| Signature hash     | SHA-256                                  | |
| Basic Constraints  | critical, `CA:TRUE`                      | CA material |
| Key Usage          | critical, `keyCertSign, cRLSign`         | only signs certs/CRLs |
| Subject Key ID     | SKI set                                  | chain building |
| Lifetime           | 825 days (~27 months)                    | see §5 |
| File permissions   | `ca.key` 0600, `ca.crt` 0644             | see §4 |

The root is a pure trust anchor: it signs only the server certificate (and
CRLs if revocation is ever implemented), never end-entity traffic.

### 3.2 Server certificate (`server.crt`)

| Field              | Value                                                    |
|--------------------|----------------------------------------------------------|
| Key algorithm      | RSA 2048                                                 |
| Subject            | `/CN=home-assistance.local` (O=Kitchen LED Controller Dev) |
| Subject Alt Name   | `DNS:home-assistance.local` (exactly one entry)          |
| Extended Key Usage | `serverAuth` (TLS Web Server Authentication)             |
| Key Usage          | `digitalSignature, keyEncipherment`                      |
| Basic Constraints  | critical, `CA:FALSE`                                     |
| Lifetime           | 825 days (~27 months), capped by the CA validity         |
| File permissions   | `server.key` 0600, `server.crt` 0644, `server_key.pem` 0644 |

The leaf has no CA capability, no code/email signing, and no extra names:
it can only authenticate the ThingsBoard TLS endpoints.

## 4. Key usage and file permissions

| File                          | Mode  | Purpose / distribution                              |
|-------------------------------|-------|-----------------------------------------------------|
| `server/certs/ca.key`         | 0600  | CA signing key. Stays on this host. **Never** distributed. |
| `server/certs/ca.crt`         | 0644  | Root certificate. Public. This is the **only** PKI file devices receive (as `/cert/ca.crt`). |
| `server/certs/server.key`     | 0600  | Server private key. Host-only; handed to containers only via `server_key.pem` bind mount. |
| `server/certs/server_key.pem` | 0644  | Container copy of the server key (read by ThingsBoard uid 799 over the read-only `./certs` bind mount). |
| `server/certs/server.crt`     | 0644  | Server certificate. Public. |
| `server/certs/server.pem`     | 0644  | `server.crt` + `ca.crt` chain. Public. |
| `server/certs/server.csr`     | 0644  | Signing request. Public; kept for audit/renewal. |
| `server/certs/server.ext`     | 0644  | Signing profile used at issuance (audit). |
| `server/.env`                 | 0600  | Secrets (PostgreSQL password). Owner-only. |
| `server/data/postgres`        | —     | Durable database state, git-ignored. |

Policy: private keys are owner-only on the host (0600). The only exception is
`server_key.pem` (0644), which must be readable by the unprivileged
ThingsBoard container over the read-only bind mount — it is a throwaway
development key inside a git-ignored directory, so this is acceptable here.
Production keys follow a stricter, hardware-backed policy (see §6).

## 5. Lifetime and renewal

| Material | Lifetime | Renewal trigger                        |
|----------|----------|----------------------------------------|
| Dev CA   | 825 days | at most every ~24 months, or on compromise |
| Dev server cert | 825 days | before expiry; on key rotation        |

Renewal rules:

1. **Server certificate renewal (same CA).** Re-issue the leaf without
   rotating trust:

   ```bash
   server/scripts/gen_server_csr.sh --force
   server/scripts/gen_server_cert.sh --force
   python3 server/scripts/check_pki.py
   cd server && docker compose restart thingsboard caddy
   ```

   Devices do **not** need a new trust anchor (`/cert/ca.crt` unchanged).

2. **CA rotation.** `gen_dev_ca.sh --regenerate` (or
   `gen_dev_tls.sh --regenerate`) creates a fresh root and invalidates every
   previously distributed copy of `ca.crt`:

   - regenerate; re-issue a server CSR/certificate;
   - reinstall `ca.crt` on every device (`/cert/ca.crt`) and on admin
     browsers/REST tooling;
   - restart the stack and re-run `check_pki.py` + `check_endpoints.py`;
   - schedule the rotation before CA expiry — the server certificate must
     not outlive its signer (validated by `check_pki.py`).

3. **Calendar.** Track the `ca.crt` / `server.crt` `notAfter` dates (visible
   via `openssl x509 -in server/certs/server.crt -noout -dates`). Plan
   renewal at ≥ 90 days before expiry to leave room for device trust-store
   rollout.

4. **Compromise.** If `ca.key` or `server.key` leaves the trusted host, treat
   it as a CA/key compromise: rotate immediately and redistribute `ca.crt`
   (or the new root) to every device.

## 6. Device trust-store installation

Devices verify `mqtts://home-assistance.local:8883` with standard TLS
**chain + hostname verification** (`skip_verify` forbidden; see
`components/mqtt_cfg/README.md`). The device trust store contains exactly one
file:

```
/cert/ca.crt     <- copy of server/certs/ca.crt (public root certificate)
```

Installation rules:

1. Provision `/cert/ca.crt` on the device during manufacturing/initial
   configuration. Only the **public certificate** is copied — never
   `ca.key`, `server.key`, `server_key.pem`, or any private key.
2. Device-side config: `ca_path: /cert/ca.crt`, hostname
  `home-assistance.local`, port 8883, `skip_verify: false`.
3. `check_pki.py` verifies that no device artifact (`ca.crt`, `server.crt`,
   `server.pem`) contains a `PRIVATE KEY` block and that git tracks no
   `*.key`/`*.pem`/`*.p12` file anywhere in the repository — i.e. no device
   can receive CA or server private keys through the supported paths.
4. Firmware release images must never embed or trust development roots
   (see `SECURITY.md` and §7).

## 7. Validation — expected TLS success/failure matrix

`python3 server/scripts/check_pki.py` is a credential-free, offline
validation of the generated material. Each check and its expected outcome:

| Check                        | Expected result                    | What it proves |
|------------------------------|------------------------------------|----------------|
| trusted CA success           | `PASS` — `openssl verify -CAfile ca.crt -verify_hostname home-assistance.local server.crt` reports `OK` | The documented host verifies against the trusted root (chain + hostname). |
| unknown CA failure           | `FAIL` — the same certificate does **not** verify against an unrelated CA | A device that does not trust `ca.crt` cannot connect. |
| hostname mismatch            | `FAIL` — the certificate verified for `wrong.home-assistance.local` is rejected | SAN/hostname verification is active; skipping it is impossible. |
| DNS SAN required             | `PASS` — SAN set is exactly `{DNS:home-assistance.local}` | The certificate is not multi-purpose / multi-name. |
| CA profile                   | `PASS` — `CA:TRUE`, `keyCertSign,cRLSign` | Root is a pure trust anchor. |
| server profile               | `PASS` — `CA:FALSE`, `digitalSignature,keyEncipherment`, `serverAuth` | Leaf is TLS-server-only. |
| lifetime policy              | `PASS` — nothing expired, server ≤ CA, within 825-day caps | Renewal discipline is enforced. |
| file permissions             | `PASS` — keys 0600, certs 0644, `server_key.pem` 0644, `.env` 0600 | No world-readable private keys. |
| no private keys on devices/committed | `PASS` — no `PRIVATE KEY` in device artifacts, git tracks no `.key`/`.pem`/`.p12` | Devices/commits never receive private keys. |

Live endpoint validation (requires the compose stack):

```bash
python3 server/scripts/check_endpoints.py            # HTTPS 443 + MQTT TLS 8883
python3 server/scripts/check_endpoints.py --wait 600 # poll until ready
```

Automated regression: `python3 server/scripts/test_pki.py` generates material
into a scratch directory and asserts the full matrix above.

## 8. Production CA custody and renewal (documented procedures)

> **Boundary:** this repository contains **no production CA material**.
> The development scripts generate development-only keys; the production
> root key, intermediate keys, certificates, and CSRs are created and held
> exclusively by the production custody process below — never on the
> ThingsBoard runtime host and never in a git repository.

### 8.1 Custody model

- **Offline root CA.** The production root private key is generated on an
  air-gapped machine (no network interface attached) and stored on
  encrypted removable media kept in a safe under **dual control** (two
  authorized officers must be present for any use). The root key is
  write-once media where practical (e.g. paper/HSM-issued key shares).
- **Issuing intermediate CA.** A short-lived intermediate CA (valid ~2–3
  years) is created offline and its key is held on a signing workstation
  that is only connected to the LAN during signing ceremonies. The
  intermediate, not the root, signs server certificates.
- **Runtime host (ThingsBoard) receives only:** the server certificate(s),
  the server private key (protected at rest, ideally imported into a
  hardware HSM or the TLS reverse-proxy keystore), the CA/intermediate
  chain for client validation — and never the root private key.
- **Separation of duties:** root custody, intermediate issuance, and server
  deployment are separate roles. No single person holds both the root media
  and the runtime server access.

### 8.2 Root key generation (ceremony, offline)

1. Authorize the ceremony (change advisory board / sign-off record).
2. Boot the air-gapped machine from a trusted, verified live image.
3. Generate the root key (RSA-4096 minimum or a hardware HSM key, e.g.
   YubiHSM/Nitro) with `openssl`/HSM tooling; set a strong passphrase or
   rely on the HSM.
4. Create the self-signed root with:
   - `basicConstraints = critical, CA:TRUE, pathlen:1` (only one
     intermediate level),
   - `keyUsage = critical, keyCertSign, cRLSign` (no digitalSignature —
     the root never authenticates peers directly),
   - `subjectKeyIdentifier` set; lifetime as short as operational
     constraints allow (3–5 years) with documented rollover.
5. Export only the public certificate to a burn/read-once medium; the key
   material goes to the safe (or HSM).
6. Record in an immutable audit log: serials, dates, officers present,
   media IDs, and fingerprints (SHA-256 of the public certificate).

### 8.3 Issuance of the ThingsBoard server certificate

1. Runtime host (or reverse proxy admin) generates a fresh server private
   key (RSA-2048/ECC-P256) and a CSR with exactly
  `subjectAltName = DNS:home-assistance.local` + any explicitly approved
   additional LAN names.
2. The CSR is transferred to the signing workstation over an authenticated
   channel (USB media; check SHA-256 both ways).
3. During the signing ceremony (intermediate key unlocked by its custodians)
   the certificate is issued with:
   - `extendedKeyUsage = serverAuth`,
   - `keyUsage = digitalSignature, keyEncipherment`,
   - `basicConstraints = critical, CA:FALSE`,
   - validity ending **before** the intermediate/root validity ends.
4. The signed certificate is returned the same authenticated way; the CSR
   and certificate are archived in the PKI record (serial, subject, SAN,
   validity, revocation status).

### 8.4 Renewal and rollover

- **Server certificate renewal:** repeat §8.3 before expiry (target ≥ 90
  days). Deploy the new certificate to the reverse proxy / MQTT TLS
  listener, restart, and run the endpoint checks. Devices are unaffected —
  the trust anchor (root/intermediate) is unchanged.
- **Root/intermediate rollover:** issue the new root offline, stage a
  parallel intermediate under the old root if overlap is required, and roll
  client trust-store updates in a sequenced rollout (staging → pilot → all
  devices). Deprecate the old root only after all devices and services have
  verified with the new anchor.
- **Record keeping:** every issuance and renewal is logged (serial, subject,
  requestor, custodian, date, expiry); backups of the PKI database and the
  CA media are tested for restore, not only created.

### 8.5 Revocation and compromise

- If a server key is compromised: revoke/reissue immediately (§8.3), rotate
  the key, and audit access.
- If the intermediate key is compromised: revoke the intermediate with the
  root, issue a new intermediate, reissue all server certs.
- If the **root** key is compromised: declare full rollover (§8.4) — every
  device trust store must be re-provisioned. This is why the root is kept
  offline and under dual control.
- Public CRLs/OCSP are optional for a LAN-only deployment; at minimum,
  maintain an internal revocation list and the ability to revoke
  intermediate(s) at the root.

### 8.6 What this repository does (and does not) do

- ✅ Documents the production custody, ceremony, and renewal procedures.
- ✅ Generates **development-only** CA/server material into a git-ignored
  directory.
- ✅ Validates dev material with `check_pki.py` / `check_endpoints.py`.
- ❌ Never generates, stores, or commits production root/intermediate
  private keys or certificates.
- ❌ Never puts a private key in an image, artifact, or device build.
